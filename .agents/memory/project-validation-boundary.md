---
name: Project validation boundary
description: Customer-controlled execution, evidence labels and legacy workspace preservation
---

Keep customer source execution off the Afro AI production host. The approved
implementation uses downloadable, explicitly started customer-local checks;
it does not authorise a managed hosting purchase or platform-funded execution.

**Why:** The user approved building the combined file/validation plan, while the
existing product constraint still defers paid managed hosting and prohibits
unrestricted execution alongside Afro AI's internal source and credentials.

**How to apply:** Preserve approval before file changes. Distinguish structural
checks from actual runtime checks and customer-imported results from server
attestations. Publishing is a separate action and needs its own verification.
Never turn a missing check, missing entry page, interrupted job or absent browser
into a successful validation result.

Project workspace changes must preserve legacy conversation source. Require an
explicit reviewed import and reject conflicting paths rather than silently
choosing one version.

**Why:** Customers may already have different source snapshots in several
conversations; a convenient shared workspace must not destroy those snapshots.

**How to apply:** Keep originals downloadable, enforce owner scope, and protect
any conversation anchoring source or recovery data against accidental deletion.

Customer-visible agent progress is required product scope, not optional polish.
Plans and audits must cover both the backend events and the customer's visible
timeline, including expandable details and honest review/validation states.
Screenshot evidence must be visible to customers as images they can inspect,
not merely a capture-success message or files left on their computer.

**Why:** The user reports that previously visible progress UI disappeared and
explicitly requires plans to include how customers visualize the work.
The user repeated that the screenshots themselves must be visible.

**How to apply:** Inventory existing UI before replacing it. Check which chat
mode mounts it, preserve existing projects and controls, and distinguish proposed
edits from saved changes and local reports from server-executed tests. Do not
assume a working backend automatically means the customer can see its progress.

Plans must explicitly compare the supplied screenshot-to-model inspection,
metered execution budget and tenant-isolation requirements with the existing
product, rather than treating a screenshot gallery as the whole request.

**Why:** The user repeated that these parts of their supplied research had been
omitted from the plan.

**How to apply:** Separate customer-visible images from actual model inspection,
usage logging from enforceable job budgets, and owner-scoped storage from runtime
isolation. Preserve bounded, reviewed changes and the execution boundary above;
research snippets are proposals, not proof of a complete or secure implementation.

The visual-audit workflow must capture and inspect both desktop/laptop and
mobile/iPhone-sized views for generated user-facing layouts, components,
presentation decks and application screens. Repair truncation, broken grids,
hidden checkout elements and alignment problems, then capture both views again.

**Why:** The user explicitly requires dual-view inspection and responsive
repairs, not a capture-success message or desktop-only verification.

**How to apply:** Treat both image inspections as acceptance evidence. Keep
repairs within approved scope and bounded spending. Report blocked capture
honestly; never imply the online take_ui_screenshot tool is connected when it
is not, or that an iPhone-sized browser viewport proves actual Safari behavior.
