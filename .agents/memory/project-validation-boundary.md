---
name: Project validation boundary
description: Customer-controlled execution, evidence labels and legacy workspace preservation
---

Keep customer source execution off the Afro AI production host. The approved
implementation uses downloadable, explicitly started customer-local checks;
it does not authorise a managed hosting purchase or platform-funded execution.

**Why:** The user approved building the combined file/validation plan, while the
existing product constraint still defers paid managed hosting and prohibits
unrestricted execution alongside Afro AI's internal source and credentials.

**How to apply:** Preserve approval before file changes. Distinguish structural
checks from actual runtime checks and customer-imported results from server
attestations. Publishing is a separate action and needs its own verification.
Never turn a missing check, missing entry page, interrupted job or absent browser
into a successful validation result.

Remote visual capture is a separately authorised, isolated static-preview
exception, not permission to execute customer packages on the Afro AI host.
Require source/image sharing consent and independently verify browser-provider
permission; existing DNS, D1 or R2 credentials do not prove browser access.
Keep external page requests blocked and keep unsupported full-stack/module
projects explicitly blocked in this mode.

**Why:** The user requires screenshot-to-model inspection, while the production
execution and paid-provider constraints still apply. A compatible capture
adapter must not silently introduce managed customer hosting or paid retries.

**How to apply:** Preserve customer-local runtime checks as the default.
Separate backend implementation, successful real-provider capture, visible
frontend controls and production verification. An interrupted image review or
capture must retain an uncertain outcome rather than trigger a second paid call.

An inspector's target context and output belong to an immutable owner/project/job
record, not a shared mutable active-target file in a reusable skill directory.
The reusable manual is static, administrator-controlled instruction, not
customer runtime state or a grant to read credentials.

**Why:** A supplied routing blueprint used one target file for all customers.
Concurrent jobs could overwrite that pointer and inspect the wrong customer's
source; synchronized file writing alone does not establish isolation.

**How to apply:** Resolve identity from the authenticated session, validate
workspace ownership before every operation and bind source/profile versions to
the job. Keep exported folder manifests logical and private; do not expose
absolute platform paths or make markdown rules a substitute for enforcement.

Project workspace changes must preserve legacy conversation source. Require an
explicit reviewed import and reject conflicting paths rather than silently
choosing one version.

**Why:** Customers may already have different source snapshots in several
conversations; a convenient shared workspace must not destroy those snapshots.

**How to apply:** Keep originals downloadable, enforce owner scope, and protect
any conversation anchoring source or recovery data against accidental deletion.

Customer-visible agent progress is required product scope, not optional polish.
Plans and audits must cover both the backend events and the customer's visible
timeline, including expandable details and honest review/validation states.
Screenshot evidence must be visible to customers as images they can inspect,
not merely a capture-success message or files left on their computer.

**Why:** The user reports that previously visible progress UI disappeared and
explicitly requires plans to include how customers visualize the work.
The user repeated that the screenshots themselves must be visible.

**How to apply:** Inventory existing UI before replacing it. Check which chat
mode mounts it, preserve existing projects and controls, and distinguish proposed
edits from saved changes and local reports from server-executed tests. Do not
assume a working backend automatically means the customer can see its progress.

Plans must explicitly compare the supplied screenshot-to-model inspection,
metered execution budget and tenant-isolation requirements with the existing
product, rather than treating a screenshot gallery as the whole request.

**Why:** The user repeated that these parts of their supplied research had been
omitted from the plan.

**How to apply:** Separate customer-visible images from actual model inspection,
usage logging from enforceable job budgets, and owner-scoped storage from runtime
isolation. Preserve bounded, reviewed changes and the execution boundary above;
research snippets are proposals, not proof of a complete or secure implementation.

The visual-audit workflow must capture and inspect both desktop/laptop and
mobile/iPhone-sized views for generated user-facing layouts, components,
presentation decks and application screens. Repair truncation, broken grids,
hidden checkout elements and alignment problems, then capture both views again.

**Why:** The user explicitly requires dual-view inspection and responsive
repairs, not a capture-success message or desktop-only verification.

**How to apply:** Treat both image inspections as acceptance evidence. Keep
repairs within approved scope and bounded spending. Report blocked capture
honestly; never imply the online take_ui_screenshot tool is connected when it
is not, or that an iPhone-sized browser viewport proves actual Safari behavior.

Customers must see real execution activity and screenshot evidence inside the
project chat, not only in a separate activity log. Turning the project agent off
must not remove access to saved evidence.
The requested unified feed also includes design-proposal artifact cards and
grouped, expandable operations alongside conversational replies.

**Why:** The user repeatedly distinguished the promised in-chat client experience
from backend functionality and an activity-log-only implementation.
They also repeated that the unified frontend feed needs its own explanation,
not just an explanation of the backend artifact-emission function.

**How to apply:** Keep passive history separate from permission to execute.
Verify customer-visible integration as well as backend tests; a release is not
complete merely because its endpoints or build exist.

Customers must be able to return to older execution activity, not merely see a
recent rolling buffer restored after refresh.

**Why:** The user supplied persistence research and explicitly asked to build it.

**How to apply:** Distinguish complete stored history from a limited live view.
Disclose gaps in legacy data that was already discarded, and keep legal retention
and post-deletion archival separate from ordinary project activity persistence.

Keep the ordinary conversation primary: technical notices and optional visual
controls must not consume the main chat viewport. Collapsing those controls must
not hide saved screenshots, proposal cards, conversation replies or failure status.

**Why:** The user repeatedly rejected a technically integrated but cramped live UI
dominated by consent and capability notices; the requested experience is a clean
conversation with expandable actions and inspectable images.

**How to apply:** Check default collapsed states and both responsive layouts, not
just whether components mount. Keep permission controls real and failures honest;
hiding a capability warning does not make capture operational.

Real action icons, action names and current statuses must stay visible directly
in chat even when technical details are collapsed.

**Why:** The user explicitly reported that the live icons were still missing
after the split-screen UI update and asked to finish the UI first.

**How to apply:** Cover both incoming live operations and saved activity, not
only expanded log details. Check ordinary chat as well as project-agent mode:
the user reported unchanged chat after deployment because icons were gated on
project-tool events. Show browser-observed request/response progress in ordinary
chat, but never simulate tool activity there.
